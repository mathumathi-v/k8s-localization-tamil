<!-- overview -->

இந்தப் பக்கம் Kubernetes இல் உள்ள ServiceAccount பொருளை அறிமுகப்படுத்துகிறது. சேவை கணக்குகள் எவ்வாறு செயல்படுகின்றன, பயன்பாட்டு நிகழ்வுகள், வரம்புகள், மாற்று வழிகள் மற்றும் கூடுதல் வழிகாட்டுதலுக்கான ஆதாரங்களுக்கான இணைப்புகள் ஆகியவற்றைப் பற்றிய தகவல்களை இந்தப் பக்கம் வழங்குகிறது.

<!-- body -->

## சேவை கணக்குகள் என்றால் என்ன? {#what-are-service-accounts}

ஒரு சேவை கணக்கு என்பது மனிதர் அல்லாத (non-human) ஒரு கணக்கு வகையாகும். Kubernetes இல், இது ஒரு Kubernetes கொத்தில் (Cluster) தனித்துவமான அடையாளத்தை (identity) வழங்குகிறது. பயன்பாட்டு Pod கள், கணினி கூறுகள் மற்றும் கொத்துக்கு உள்ளே அல்லது வெளியே உள்ள நிறுவனங்கள் ஒரு குறிப்பிட்ட ServiceAccount இன் நற்சான்றிதழ்களை (credentials) பயன்படுத்தி அந்த ServiceAccount ஆக தம்மை அடையாளப்படுத்திக்கொள்ளலாம். API சேவையகத்தில் அங்கீகாரம் (Authentication) பெறுவது அல்லது அடையாளம் சார்ந்த பாதுகாப்புக் கொள்கைகளை நடைமுறைப்படுத்துவது போன்ற பல்வேறு சூழல்களில் இந்த அடையாளம் பயனுள்ளதாக இருக்கிறது.

சேவை கணக்குகள் API சேவையகத்தில் ServiceAccount பொருட்களாக இருக்கின்றன. சேவை கணக்குகளுக்கு பின்வரும் பண்புகள் உள்ளன:

* **பெயரிடல் வெளி சார்ந்தது (Namespaced):** ஒவ்வொரு சேவை கணக்கும் ஒரு Kubernetes
  {{<glossary_tooltip text="namespace" term_id="namespace">}} உடன் இணைக்கப்படுகிறது. ஒவ்வொரு பெயரிடல் வெளியும் (Namespace) உருவாக்கப்படும்போது தானாகவே ஒரு [`default` ServiceAccount](#default-service-accounts) பெறுகிறது.

* **இலகுரகமானது (Lightweight):** சேவை கணக்குகள் கொத்தில் இருக்கின்றன மற்றும் Kubernetes API இல் வரையறுக்கப்படுகின்றன. குறிப்பிட்ட பணிகளை இயக்குவதற்கு சேவை கணக்குகளை விரைவாக உருவாக்கலாம்.

* **எளிதில் மாற்றத்தக்கது (Portable):** ஒரு சிக்கலான கொள்கலன் (Container) பணிச்சுமையின் (Workload) கட்டமைப்பு தொகுப்பில் அமைப்பின் கூறுகளுக்கான சேவை கணக்கு வரையறைகள் இருக்கலாம். சேவை கணக்குகளின் இலகுரக தன்மை மற்றும் பெயரிடல் வெளி (Namespace) சார்ந்த அடையாளங்கள் கட்டமைப்புகளை எளிதில் மாற்றத்தக்கதாக ஆக்குகின்றன.

சேவை கணக்குகள், கொத்தில் அங்கீகரிக்கப்பட்ட மனித பயனர்களான பயனர் கணக்குகளிலிருந்து (user accounts) வேறுபட்டவை. இயல்பாக, பயனர் கணக்குகள் Kubernetes API சேவையகத்தில் இல்லை; அதற்கு பதிலாக, API சேவையகம் பயனர் அடையாளங்களை முக்கியமற்ற தரவாக கருதுகிறது. பல முறைகளைப் பயன்படுத்தி நீங்கள் பயனர் கணக்காக அங்கீகாரம் (Authentication) பெறலாம். சில Kubernetes விநியோகங்கள் API சேவையகத்தில் பயனர் கணக்குகளை பிரதிநிதித்துவப்படுத்த தனிப்பயன் நீட்டிப்பு API கூட்டும்.

### இயல்புநிலை சேவை கணக்குகள் (Default service accounts) {#default-service-accounts}

நீங்கள் ஒரு கொத்தை உருவாக்கும்போது, Kubernetes உங்கள் கொத்தில் உள்ள ஒவ்வொரு பெயரிடல் வெளிக்கும் (Namespace) தானாகவே `default` என்ற பெயரிடப்பட்ட ஒரு ServiceAccount பொருளை உருவாக்குகிறது. ஒவ்வொரு பெயரிடல் வெளியிலும் உள்ள `default` சேவை கணக்குகளுக்கு, RBAC இயக்கப்பட்டிருந்தால் Kubernetes அனைத்து அங்கீகரிக்கப்பட்ட முதன்மையினர்களுக்கும் வழங்கும் [இயல்புநிலை API கண்டுபிடிப்பு அனுமதிகளைத்](/docs/reference/access-authn-authz/rbac/#default-roles-and-role-bindings) தவிர வேறு எந்த அனுமதிகளும் இயல்பாக வழங்கப்படுவதில்லை. நீங்கள் ஒரு பெயரிடல் வெளியில் உள்ள `default` ServiceAccount பொருளை நீக்கினால்,
{{< glossary_tooltip text="control plane" term_id="control-plane" >}}
அதை ஒரு புதியதால் மாற்றுகிறது.

நீங்கள் ஒரு பெயரிடல் வெளியில் ஒரு Pod ஐ பயன்படுத்தினால், மற்றும் [Pod க்கு கைமுறையாக ஒரு ServiceAccount ஒதுக்கவில்லை](#assign-to-pod) என்றால், Kubernetes அந்த பெயரிடல் வெளிக்கான `default` ServiceAccount ஐ Pod க்கு ஒதுக்குகிறது.

## Kubernetes சேவை கணக்குகளுக்கான பயன்பாட்டு நிகழ்வுகள் {#use-cases}

பொதுவான வழிகாட்டியாக, பின்வரும் சூழல்களில் அடையாளங்களை வழங்க சேவை கணக்குகளை பயன்படுத்தலாம்:

* உங்கள் Pod கள் Kubernetes API சேவையகத்துடன் தொடர்புகொள்ள வேண்டும், எடுத்துக்காட்டாக பின்வரும் சூழல்களில்:
  * Secret களில் சேமிக்கப்பட்ட முக்கியமான தகவல்களுக்கு படிக்க மட்டும் (read-only) அணுகல் வழங்குதல்.
  * [குறுக்கு-பெயரிடல் வெளி அணுகல் (cross-namespace access)](#cross-namespace) வழங்குதல், எடுத்துக்காட்டாக `example` பெயரிடல் வெளியில் உள்ள ஒரு Pod ஐ `kube-node-lease` பெயரிடல் வெளியில் உள்ள Lease பொருட்களை படிக்க, பட்டியலிட மற்றும் கண்காணிக்க அனுமதித்தல்.
* உங்கள் Pod கள் வெளிப்புற சேவையுடன் தொடர்புகொள்ள வேண்டும். எடுத்துக்காட்டாக, ஒரு பணிச்சுமை Pod க்கு வணிகரீதியான கிளவுட் API க்கான அடையாளம் தேவை, மேலும் வணிக வழங்குநர் பொருத்தமான நம்பிக்கை உறவை கட்டமைக்க அனுமதிக்கிறார்.
* [`imagePullSecret` ஐ பயன்படுத்தி தனிப்பட்ட படப் பதிவேட்டில் அங்கீகாரம் (Authentication) பெறுதல்](/docs/tasks/configure-pod-container/configure-service-account/#add-imagepullsecrets-to-a-service-account).
* ஒரு வெளிப்புற சேவை Kubernetes API சேவையகத்துடன் தொடர்புகொள்ள வேண்டும். எடுத்துக்காட்டாக, CI/CD பைப்லைனின் ஒரு பகுதியாக கொத்தில் அங்கீகாரம் (Authentication) பெறுதல்.
* வெவ்வேறு Pod களை வெவ்வேறு சூழல்களில் தொகுக்க வெவ்வேறு Pod களின் ServiceAccount அடையாளத்தை நம்பியிருக்கும் மூன்றாம்-தரப்பு பாதுகாப்பு மென்பொருளை நீங்கள் உங்கள் கொத்தில் பயன்படுத்துகிறீர்கள்.

## சேவை கணக்குகளை எவ்வாறு பயன்படுத்துவது {#how-to-use}

Kubernetes சேவை கணக்கை பயன்படுத்த, நீங்கள் பின்வருவனவற்றைச் செய்கிறீர்கள்:

1. `kubectl` போன்ற Kubernetes கிளையன்ட் அல்லது பொருளை வரையறுக்கும் மேனிஃபெஸ்டைப் பயன்படுத்தி ஒரு ServiceAccount பொருளை உருவாக்குங்கள்.
1. [RBAC](/docs/reference/access-authn-authz/rbac/) போன்ற அனுமதி (Authorization) வழிமுறையைப் பயன்படுத்தி ServiceAccount பொருளுக்கு அனுமதிகளை வழங்குங்கள்.
1. Pod உருவாக்கும்போது ServiceAccount பொருளை Pod களுடன் இணைக்கவும்.

   நீங்கள் வெளிப்புற சேவையிலிருந்து அடையாளத்தை பயன்படுத்தினால்,
   [ServiceAccount டோக்கனை (Token) மீட்டெடுங்கள்](#get-a-token) மற்றும் அந்த சேவையிலிருந்து அதை பயன்படுத்துங்கள்.

வழிமுறைகளுக்கு,
[Pod களுக்கான சேவை கணக்குகளை கட்டமைத்தல்](/docs/tasks/configure-pod-container/configure-service-account/) ஐ பார்க்கவும்.

### ServiceAccount க்கு அனுமதிகளை வழங்குதல் {#grant-permissions}

ஒவ்வொரு சேவை கணக்கிற்கும் தேவையான குறைந்தபட்ச அனுமதிகளை வழங்க நீங்கள் உள்ளமைக்கப்பட்ட Kubernetes
[பங்கு அடிப்படையிலான அணுகல் கட்டுப்பாடு (role-based access control — RBAC)](/docs/reference/access-authn-authz/rbac/)
வழிமுறையை பயன்படுத்தலாம். நீங்கள் ஒரு *பங்கை (role)* உருவாக்குகிறீர்கள், இது அணுகலை வழங்குகிறது, பின்னர் உங்கள் ServiceAccount உடன் பங்கை *இணைக்கிறீர்கள் (bind)*. RBAC உங்களுக்கு குறைந்தபட்ச அனுமதிகளை வரையறுக்க அனுமதிக்கிறது, இதனால் சேவை கணக்கு அனுமதிகள் குறைந்தபட்ச சலுகை கொள்கையை (principle of least privilege) பின்பற்றுகின்றன. அந்த சேவை கணக்கை பயன்படுத்தும் Pod கள் சரியாக செயல்படத் தேவையான அனுமதிகளை விட அதிகமான அனுமதிகளைப் பெறுவதில்லை.

வழிமுறைகளுக்கு,
[ServiceAccount அனுமதிகள்](/docs/reference/access-authn-authz/rbac/#service-account-permissions) ஐ பார்க்கவும்.

#### ServiceAccount ஐ பயன்படுத்தி குறுக்கு-பெயரிடல் வெளி அணுகல் (Cross-namespace access) {#cross-namespace}

ஒரு பெயரிடல் வெளியில் உள்ள சேவை கணக்குகளை கொத்தில் வேறொரு பெயரிடல் வெளியில் உள்ள வளங்களில் செயல்களை செய்ய அனுமதிக்க RBAC ஐ பயன்படுத்தலாம். எடுத்துக்காட்டாக, `dev` பெயரிடல் வெளியில் ஒரு சேவை கணக்கும் Pod உம் இருக்கும் சூழலை கவனியுங்கள், மேலும் உங்கள் Pod ஆனது `maintenance` பெயரிடல் வெளியில் இயங்கும் Job களை பார்க்க வேண்டும் என விரும்புகிறீர்கள். Job பொருட்களை பட்டியலிட அனுமதிகளை வழங்கும் ஒரு Role பொருளை உருவாக்கலாம். பின்னர், `maintenance` பெயரிடல் வெளியில் Role ஐ ServiceAccount பொருளுடன் இணைக்க ஒரு RoleBinding பொருளை உருவாக்குவீர்கள். இப்போது, `dev` பெயரிடல் வெளியில் உள்ள Pod கள் அந்த சேவை கணக்கை பயன்படுத்தி `maintenance` பெயரிடல் வெளியில் உள்ள Job பொருட்களை பட்டியலிடலாம்.

### Pod க்கு ServiceAccount ஒதுக்குதல் {#assign-to-pod}

Pod க்கு ஒரு ServiceAccount ஒதுக்க, Pod விவரக்குறிப்பில் `spec.serviceAccountName` புலத்தை அமைக்கிறீர்கள். Kubernetes பின்னர் தானாகவே அந்த ServiceAccount க்கான நற்சான்றிதழ்களை Pod க்கு வழங்குகிறது. v1.22 மற்றும் அதற்கு பிந்தைய பதிப்புகளில், Kubernetes `TokenRequest` API ஐ பயன்படுத்தி குறுகிய-கால, **தானாகவே சுழலும் (automatically rotating)** டோக்கனை (Token) பெறுகிறது மற்றும் டோக்கனை ஒரு
[திட்டமிடப்பட்ட தொகுதியாக (projected volume)](/docs/concepts/storage/projected-volumes/#serviceaccounttoken) ஏற்றுகிறது.

இயல்பாக, Kubernetes ஆனது, `default` ServiceAccount ஆக இருந்தாலும் அல்லது நீங்கள் குறிப்பிடும் தனிப்பயன் ServiceAccount ஆக இருந்தாலும், ஒதுக்கப்பட்ட ServiceAccount க்கான நற்சான்றிதழ்களை Pod க்கு வழங்குகிறது.

குறிப்பிட்ட ServiceAccount அல்லது `default` ServiceAccount க்கான நற்சான்றிதழ்களை Kubernetes தானாகவே செலுத்துவதை தடுக்க, உங்கள் Pod விவரக்குறிப்பில் `automountServiceAccountToken` புலத்தை `false` என அமைக்கவும்.

1.22 க்கு முந்தைய பதிப்புகளில், Kubernetes ஆனது Pod க்கு Secret ஆக நீண்ட-கால, நிலையான டோக்கனை (Token) வழங்குகிறது.

#### ServiceAccount நற்சான்றிதழ்களை கைமுறையாக மீட்டெடுத்தல் {#get-a-token}

நிலையான இடத்தில் அல்லாத இடத்தில் ஏற்றுவதற்கு அல்லது API சேவையகம் அல்லாத பார்வையாளருக்கான ServiceAccount க்கான நற்சான்றிதழ்கள் தேவைப்பட்டால், பின்வரும் முறைகளில் ஒன்றை பயன்படுத்தவும்:

* [TokenRequest API](/docs/reference/kubernetes-api/authentication-resources/token-request-v1/)
  (பரிந்துரைக்கப்படுகிறது): உங்கள் சொந்த *பயன்பாட்டு குறியீட்டிலிருந்தே* குறுகிய-கால சேவை கணக்கு டோக்கனை கோருங்கள். டோக்கன் தானாகவே காலாவதியாகிறது மற்றும் காலாவதியான பின்னர் சுழலும்.
  Kubernetes பற்றி தெரியாத பழைய பயன்பாடு இருந்தால், இந்த டோக்கன்களை பெற்று பயன்பாட்டு பணிச்சுமைக்கு கிடைக்கும்படி செய்ய அதே pod க்குள் ஒரு sidecar கொள்கலனை (Container) பயன்படுத்தலாம்.
* [Token Volume Projection](/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection)
  (பரிந்துரைக்கப்படுகிறது): Kubernetes v1.20 மற்றும் அதற்கு பிந்தைய பதிப்புகளில், சேவை கணக்கு டோக்கனை Pod க்கு ஒரு *திட்டமிடப்பட்ட தொகுதியாக (projected volume)* சேர்க்க kubelet க்கு சொல்ல Pod விவரக்குறிப்பை பயன்படுத்துங்கள். திட்டமிடப்பட்ட டோக்கன்கள் தானாகவே காலாவதியாகின்றன, மேலும் காலாவதியாவதற்கு முன் kubelet டோக்கனை சுழல்கிறது.
* [Service Account Token Secrets](/docs/tasks/configure-pod-container/configure-service-account/#manually-create-an-api-token-for-a-serviceaccount)
  (பரிந்துரைக்கப்படவில்லை): Pod களில் Kubernetes Secret களாக சேவை கணக்கு டோக்கன்களை ஏற்றலாம். இந்த டோக்கன்கள் காலாவதியாவதில்லை மற்றும் சுழல்வதில்லை. v1.24 க்கு முந்தைய பதிப்புகளில், ஒவ்வொரு சேவை கணக்கிற்கும் தானாகவே ஒரு நிரந்தர டோக்கன் உருவாக்கப்பட்டது. நிலையான, நீண்ட-கால நற்சான்றிதழ்களுடன் தொடர்புடைய அபாயங்கள் காரணமாக, குறிப்பாக பெரிய அளவில், இந்த முறை இனி பரிந்துரைக்கப்படவில்லை. [LegacyServiceAccountTokenNoAutoGeneration feature gate](/docs/reference/command-line-tools-reference/feature-gates-removed)
  (இது Kubernetes v1.24 முதல் v1.26 வரை இயல்பாக இயக்கப்பட்டிருந்தது), ServiceAccount களுக்கு இந்த டோக்கன்களை தானாகவே உருவாக்குவதை Kubernetes க்கு தடுத்தது. feature gate ஆனது v1.27 இல் நீக்கப்படுகிறது, ஏனெனில் அது GA நிலைக்கு உயர்த்தப்பட்டது; இன்னும் கைமுறையாக காலவரையற்ற சேவை கணக்கு டோக்கன்களை உருவாக்கலாம், ஆனால் பாதுகாப்பு தாக்கங்களை கணக்கில் எடுத்துக்கொள்ள வேண்டும்.

{{< note >}}
உங்கள் Kubernetes கொத்துக்கு வெளியே இயங்கும் பயன்பாடுகளுக்கு, Secret ல் சேமிக்கப்படும் நீண்ட-கால ServiceAccount டோக்கனை உருவாக்குவதை பரிசீலிக்கலாம். இது அங்கீகாரம் (Authentication) பெற அனுமதிக்கிறது, ஆனால் Kubernetes திட்டம் இந்த அணுகுமுறையை தவிர்க்க பரிந்துரைக்கிறது.
நீண்ட-கால bearer டோக்கன்கள் ஒரு பாதுகாப்பு அபாயத்தை ஏற்படுத்துகின்றன, ஏனெனில் ஒருமுறை வெளிப்பட்டால், டோக்கன் தவறாக பயன்படுத்தப்படலாம். அதற்கு பதிலாக, ஒரு மாற்றை பரிசீலியுங்கள். எடுத்துக்காட்டாக, உங்கள் வெளிப்புற பயன்பாடு நன்கு பாதுகாக்கப்பட்ட தனிப்பட்ட விசை `மற்றும்` சான்றிதழைப் பயன்படுத்தி அல்லது நீங்களே நடைமுறைப்படுத்தும் [அங்கீகார webhook](/docs/reference/access-authn-authz/authentication/#webhook-token-authentication) போன்ற தனிப்பயன் வழிமுறையைப் பயன்படுத்தி அங்கீகாரம் (Authentication) பெறலாம்.

உங்கள் வெளிப்புற பயன்பாட்டிற்கு குறுகிய-கால டோக்கன்களை பெற TokenRequest ஐயும் பயன்படுத்தலாம்.
{{< /note >}}

### Secret களுக்கான அணுகலை கட்டுப்படுத்துதல் (நிராகரிக்கப்பட்டது) {#enforce-mountable-secrets}

{{< feature-state for_k8s_version="v1.32" state="deprecated" >}}

{{< note >}}
`kubernetes.io/enforce-mountable-secrets` Kubernetes v1.32 முதல் நிராகரிக்கப்படுகிறது. ஏற்றப்பட்ட secret களுக்கான அணுகலை தனிமைப்படுத்த தனித்தனி பெயரிடல் வெளிகளை (Namespaces) பயன்படுத்துங்கள்.
{{< /note >}}

Kubernetes ஆனது `kubernetes.io/enforce-mountable-secrets` என்ற குறிப்பீட்டை (annotation) வழங்குகிறது, இதை உங்கள் ServiceAccount களில் சேர்க்கலாம். இந்த குறிப்பீடு பயன்படுத்தப்படும்போது, ServiceAccount இன் secret கள் குறிப்பிட்ட வகை வளங்களில் மட்டுமே ஏற்றப்படலாம், இது உங்கள் கொத்தின் பாதுகாப்பு நிலையை மேம்படுத்துகிறது.

மேனிஃபெஸ்டைப் பயன்படுத்தி ServiceAccount க்கு குறிப்பீட்டை சேர்க்கலாம்:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  annotations:
    kubernetes.io/enforce-mountable-secrets: "true"
  name: my-serviceaccount
  namespace: my-namespace
```

இந்த குறிப்பீடு "true" என அமைக்கப்படும்போது, Kubernetes கட்டுப்பாட்டு தளம் (Control Plane) இந்த ServiceAccount இலிருந்து உள்ள Secret கள் சில ஏற்றுதல் கட்டுப்பாடுகளுக்கு உட்பட்டதை உறுதிசெய்கிறது.

1. Pod இல் ஒரு தொகுதியாக (volume) ஏற்றப்படும் ஒவ்வொரு Secret இன் பெயரும் Pod இன் ServiceAccount இன் `secrets` புலத்தில் தோன்ற வேண்டும்.
1. Pod இல் `envFrom` ஐ பயன்படுத்தி குறிப்பிடப்படும் ஒவ்வொரு Secret இன் பெயரும் Pod இன் ServiceAccount இன் `secrets` புலத்தில் தோன்ற வேண்டும்.
1. Pod இல் `imagePullSecrets` ஐ பயன்படுத்தி குறிப்பிடப்படும் ஒவ்வொரு Secret இன் பெயரும் Pod இன் ServiceAccount இன் `secrets` புலத்தில் தோன்ற வேண்டும்.

இந்த கட்டுப்பாடுகளை புரிந்துகொண்டு நடைமுறைப்படுத்துவதன் மூலம், கொத்து நிர்வாகிகள் இறுக்கமான பாதுகாப்பு சுயவிவரத்தை பராமரிக்கலாம் மற்றும் secret கள் பொருத்தமான வளங்களால் மட்டுமே அணுகப்படுவதை உறுதிசெய்யலாம்.

## சேவை கணக்கு நற்சான்றிதழ்களை அங்கீகரித்தல் {#authenticating-credentials}

ServiceAccount கள் Kubernetes API சேவையகத்தில் அங்கீகாரம் (Authentication) பெறவும், நம்பிக்கை உறவு இருக்கும் வேறு எந்த அமைப்பிலும் அங்கீகாரம் பெறவும் கையொப்பமிடப்பட்ட
{{<glossary_tooltip term_id="jwt" text="JSON Web Tokens">}} (JWT கள்) ஐப் பயன்படுத்துகின்றன.
டோக்கன் எவ்வாறு வழங்கப்பட்டது என்பதைப் பொறுத்து (`TokenRequest` ஐ பயன்படுத்தி காலவரையறை உள்ளதாக அல்லது Secret உடன் மரபு வழிமுறையைப் பயன்படுத்தி), ஒரு ServiceAccount டோக்கனுக்கு காலாவதி நேரம், பார்வையாளர் மற்றும் டோக்கன் செல்லுபடியாகத் *தொடங்கும்* நேரம் போன்றவை இருக்கலாம். ServiceAccount ஆக செயல்படும் ஒரு கிளையன்ட் Kubernetes API சேவையகத்துடன் தொடர்புகொள்ள முயற்சிக்கும்போது, HTTP கோரிக்கையுடன் கிளையன்ட் `Authorization: Bearer <token>` தலைப்பை சேர்க்கிறது. API சேவையகம் அந்த bearer டோக்கனின் செல்லுபடியை பின்வருமாறு சரிபார்க்கிறது:

1. டோக்கன் கையொப்பத்தை சரிபார்க்கிறது.
1. டோக்கன் காலாவதியானதா என சரிபார்க்கிறது.
1. டோக்கன் உரிமைகோரல்களில் உள்ள பொருள் குறிப்புகள் தற்போது செல்லுபடியானதா என சரிபார்க்கிறது.
1. டோக்கன் தற்போது செல்லுபடியானதா என சரிபார்க்கிறது.
1. பார்வையாளர் உரிமைகோரல்களை சரிபார்க்கிறது.

TokenRequest API ஆனது ஒரு ServiceAccount க்காக _கட்டுண்ட டோக்கன்களை (bound tokens)_ உற்பத்தி செய்கிறது. இந்த இணைப்பு, அந்த ServiceAccount ஆக செயல்படும் Pod போன்ற கிளையன்டின் வாழ்நாளுடன் இணைக்கப்படுகிறது. கட்டுண்ட pod சேவை கணக்கு டோக்கனின் JWT திட்டம் மற்றும் payload க்கான எடுத்துக்காட்டுக்கு [Token Volume Projection](/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection) ஐ பாருங்கள்.

`TokenRequest` API ஐ பயன்படுத்தி வழங்கப்பட்ட டோக்கன்களுக்கு, ServiceAccount ஐ பயன்படுத்தும் குறிப்பிட்ட பொருள் குறிப்பு இன்னும் இருக்கிறதா என்பதையும் API சேவையகம் சரிபார்க்கிறது, அந்த பொருளின் {{< glossary_tooltip term_id="uid" text="unique ID" >}} மூலம் பொருத்துகிறது. Pod களில் Secret களாக ஏற்றப்பட்ட மரபு டோக்கன்களுக்கு, API சேவையகம் Secret க்கு எதிராக டோக்கனை சரிபார்க்கிறது.

அங்கீகார (Authentication) செயல்முறை பற்றிய மேலும் தகவலுக்கு,
[அங்கீகாரம்](/docs/reference/access-authn-authz/authentication/#service-account-tokens) ஐ பார்க்கவும்.

### உங்கள் சொந்த குறியீட்டில் சேவை கணக்கு நற்சான்றிதழ்களை அங்கீகரித்தல் {#authenticating-in-code}

Kubernetes சேவை கணக்கு நற்சான்றிதழ்களை சரிபார்க்க வேண்டிய சொந்த சேவைகள் இருந்தால், பின்வரும் முறைகளை பயன்படுத்தலாம்:

* [TokenReview API](/docs/reference/kubernetes-api/authentication-resources/token-review-v1/)
  (பரிந்துரைக்கப்படுகிறது)
* OIDC discovery

Kubernetes திட்டம் TokenReview API ஐ பயன்படுத்த பரிந்துரைக்கிறது, ஏனெனில் இந்த முறை Secret கள், ServiceAccount கள், Pod கள் அல்லது Node கள் போன்ற API பொருட்களுடன் இணைக்கப்பட்ட டோக்கன்களை அந்த பொருட்கள் நீக்கப்படும்போது செல்லாததாக்குகிறது. எடுத்துக்காட்டாக, திட்டமிடப்பட்ட ServiceAccount டோக்கனை கொண்ட Pod ஐ நீக்கினால், கொத்து அந்த டோக்கனை உடனடியாக செல்லாததாக்குகிறது மற்றும் TokenReview உடனடியாக தோல்வியடைகிறது.
OIDC சரிபார்ப்பை பயன்படுத்தினால், டோக்கன் அதன் காலாவதி நேரத்தை அடையும் வரை உங்கள் கிளையன்ட்கள் டோக்கனை செல்லுபடியானதாக கருதுவார்கள்.

உங்கள் பயன்பாடு எப்போதும் அது ஏற்றுக்கொள்ளும் பார்வையாளரை வரையறுக்க வேண்டும், மேலும் டோக்கனின் பார்வையாளர்கள் பயன்பாடு எதிர்பார்க்கும் பார்வையாளர்களுடன் பொருந்துகிறதா என சரிபார்க்க வேண்டும். இது டோக்கனின் நோக்கத்தை குறைக்க உதவுகிறது, இதனால் அது உங்கள் பயன்பாட்டில் மட்டுமே பயன்படுத்தப்படலாம், வேறு எங்கும் இல்லை.

## மாற்றுகள் (Alternatives)

* வேறு வழிமுறையைப் பயன்படுத்தி உங்கள் சொந்த டோக்கன்களை வழங்குங்கள், பின்னர் உங்கள் சொந்த சரிபார்ப்பு சேவையைப் பயன்படுத்தி bearer டோக்கன்களை சரிபார்க்க
  [Webhook Token Authentication](/docs/reference/access-authn-authz/authentication/#webhook-token-authentication)
  ஐ பயன்படுத்துங்கள்.
* Pod களுக்கு உங்கள் சொந்த அடையாளங்களை வழங்குங்கள்.
  * [SPIFFE SVIDs ஐ X.509 சான்றிதழ் ஜோடிகளாக Pod களுக்கு வழங்க SPIFFE CSI driver plugin ஐ பயன்படுத்துங்கள்](https://cert-manager.io/docs/projects/csi-driver-spiffe/).
    {{% thirdparty-content single="true" %}}
  * [சான்றிதழ்களை Pod களுக்கு வழங்க Istio போன்ற service mesh ஐ பயன்படுத்துங்கள்](https://istio.io/latest/docs/tasks/security/cert-management/plugin-ca-cert/).
* சேவை கணக்கு டோக்கன்களை பயன்படுத்தாமல் கொத்துக்கு வெளியிலிருந்து API சேவையகத்தில் அங்கீகாரம் (Authentication) பெறுங்கள்:
  * [உங்கள் அடையாள வழங்குநரிடமிருந்து OpenID Connect (OIDC) டோக்கன்களை ஏற்க API சேவையகத்தை கட்டமைக்கவும்](/docs/reference/access-authn-authz/authentication/#openid-connect-tokens).
  * உங்கள் கொத்தில் அங்கீகாரம் (Authentication) பெற கிளவுட் வழங்குநரிடமிருந்து போன்ற வெளிப்புற Identity and Access Management (IAM) சேவையைப் பயன்படுத்தி உருவாக்கப்பட்ட சேவை கணக்குகள் அல்லது பயனர் கணக்குகளை பயன்படுத்துங்கள்.
  * [கிளையன்ட் சான்றிதழ்களுடன் CertificateSigningRequest API ஐ பயன்படுத்துங்கள்](/docs/tasks/tls/managing-tls-in-a-cluster/).
* [படப் பதிவேட்டிலிருந்து நற்சான்றிதழ்களை மீட்டெடுக்க kubelet ஐ கட்டமைக்கவும்](/docs/tasks/administer-cluster/kubelet-credential-provider/).
* அங்கீகாரம் (Authentication) பெற தனிப்பட்ட விசையைப் பயன்படுத்தி virtual Trusted Platform Module (TPM) ஐ அணுக ஒரு Device Plugin ஐ பயன்படுத்துங்கள்.
