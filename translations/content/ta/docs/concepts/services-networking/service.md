{{< glossary_definition term_id="service" length="short" prepend="Kubernetes-இல், ஒரு Service என்பது" >}}

Kubernetes-இல் Service-களின் முக்கிய நோக்கம் என்னவென்றால், அறிமுகமில்லாத சேவை கண்டறிதல் வழிமுறையைப் பயன்படுத்த உங்கள் ஏற்கனவே உள்ள பயன்பாட்டை மாற்ற வேண்டிய அவசியமில்லை. இது cloud-native உலகத்திற்காக வடிவமைக்கப்பட்ட குறியீடாக இருந்தாலும், அல்லது நீங்கள் கொள்கலன் (container) மயமாக்கிய பழைய பயன்பாடாக இருந்தாலும், Pod-களில் குறியீட்டை இயக்கலாம். அந்த Pod-களின் தொகுப்பை நெட்வொர்க்கில் கிடைக்கச் செய்ய நீங்கள் ஒரு Service-ஐ பயன்படுத்துகிறீர்கள், இதனால் வாடிக்கையாளர்கள் அதனுடன் தொடர்பு கொள்ள முடியும்.

நீங்கள் உங்கள் பயன்பாட்டை இயக்க {{< glossary_tooltip term_id="deployment" >}} பயன்படுத்தினால், அந்த Deployment Pod-களை மாறும் வகையில் உருவாக்கவும் அழிக்கவும் முடியும். ஒரு தருணத்திலிருந்து அடுத்த தருணத்திற்கு, அந்த Pod-களில் எத்தனை வேலை செய்கின்றன மற்றும் ஆரோக்கியமாக உள்ளன என்பது உங்களுக்குத் தெரியாது; அந்த ஆரோக்கியமான Pod-களின் பெயர்கள் கூட உங்களுக்குத் தெரியாமல் இருக்கலாம். Kubernetes Pod-கள் உங்கள் கொத்தின் (cluster) விரும்பிய நிலைக்கு ஏற்ப உருவாக்கப்படுகின்றன மற்றும் அழிக்கப்படுகின்றன. Pod-கள் நிலையற்ற வளங்கள் ஆகும் (ஒரு தனிப்பட்ட Pod நம்பகமானது மற்றும் நீடித்தது என்று எதிர்பார்க்கக் கூடாது).

ஒவ்வொரு Pod-க்கும் அதன் சொந்த IP முகவரி கிடைக்கிறது. உங்கள் கொத்தில் கொடுக்கப்பட்ட Deployment-க்கு, ஒரு தருணத்தில் இயங்கும் Pod-களின் தொகுப்பு, அடுத்த தருணத்தில் அந்த பயன்பாட்டை இயக்கும் Pod-களின் தொகுப்பிலிருந்து வேறுபட்டிருக்கலாம்.

இது ஒரு சிக்கலுக்கு வழிவகுக்கிறது: சில Pod-கள் (அவற்றை "backend-கள்" என்று அழைப்போம்) உங்கள் கொத்துக்குள் மற்ற Pod-களுக்கு ("frontend-கள்") செயல்பாட்டை வழங்கினால், frontend-கள் எந்த IP முகவரியுடன் இணைக்க வேண்டும் என்பதை எவ்வாறு கண்டறிந்து கண்காணிப்பது, frontend பணிச்சுமையின் backend பகுதியைப் பயன்படுத்த முடியும்?

இங்குதான் _Service-கள்_ வருகின்றன.

## Kubernetes-இல் Service-கள்

Service API, Kubernetes-இன் ஒரு பகுதியாக, Pod-களின் குழுக்களை நெட்வொர்க்கில் வெளிப்படுத்த உதவும் ஒரு சுருக்கமாகும் (abstraction). ஒவ்வொரு Service பொருளும் முனைப்புள்ளிகளின் (endpoints, வழக்கமாக இவை Pod-கள்) தர்க்கரீதியான தொகுப்பையும், அந்த Pod-களை எவ்வாறு அணுகக்கூடியதாக்குவது என்பது பற்றிய கொள்கையையும் வரையறுக்கிறது.

எடுத்துக்காட்டாக, 3 பிரதிகளுடன் இயங்கும் stateless பட-செயலாக்க backend-ஐ கருத்தில் கொள்ளுங்கள். அந்த பிரதிகள் பரிமாற்றக்கூடியவை — frontend-கள் எந்த backend-ஐ பயன்படுத்துகின்றன என்பது முக்கியமல்ல. backend தொகுப்பை உருவாக்கும் உண்மையான Pod-கள் மாறலாம் என்றாலும், frontend வாடிக்கையாளர்கள் அதைப் பற்றி அறிந்திருக்க வேண்டிய அவசியமில்லை, மேலும் அவர்கள் backend-களின் தொகுப்பை தாங்களே கண்காணிக்க வேண்டிய அவசியமும் இல்லை.

Service சுருக்கம் இந்த பிரிப்பை (decoupling) செயல்படுத்துகிறது.

ஒரு Service-ஆல் குறிவைக்கப்படும் Pod-களின் தொகுப்பு வழக்கமாக நீங்கள் வரையறுக்கும் {{< glossary_tooltip text="தேர்வாளரால்" term_id="selector" >}} தீர்மானிக்கப்படுகிறது. Service முனைப்புள்ளிகளை வரையறுக்க மற்ற வழிகளைப் பற்றி அறிய, [தேர்வாளர்கள் _இல்லாத_ Service-கள்](#services-without-selectors) பகுதியைப் பாருங்கள்.

உங்கள் பணிச்சுமை HTTP பேசினால், இணைய போக்குவரத்து அந்த பணிச்சுமையை எவ்வாறு அடைகிறது என்பதைக் கட்டுப்படுத்த [Ingress](/docs/concepts/services-networking/ingress/) பயன்படுத்த நீங்கள் தேர்வு செய்யலாம். Ingress ஒரு Service வகை அல்ல, ஆனால் இது உங்கள் கொத்துக்கான நுழைவு புள்ளியாக செயல்படுகிறது.

Kubernetes-க்கான [Gateway](https://gateway-api.sigs.k8s.io/#what-is-the-gateway-api) API, Ingress மற்றும் Service-க்கு அப்பால் கூடுதல் திறன்களை வழங்குகிறது.

### Cloud-native சேவை கண்டறிதல்

உங்கள் பயன்பாட்டில் சேவை கண்டறிதலுக்கு Kubernetes API-களைப் பயன்படுத்த முடிந்தால், பொருத்தமான EndpointSlice-களுக்காக {{< glossary_tooltip text="API server" term_id="kube-apiserver" >}}-ஐ வினவலாம். ஒரு Service-இல் உள்ள Pod-களின் தொகுப்பு மாறும்போதெல்லாம் Kubernetes அந்த Service-க்கான EndpointSlice-களைப் புதுப்பிக்கிறது.

நேரடி Kubernetes அல்லாத பயன்பாடுகளுக்கு, உங்கள் பயன்பாட்டிற்கும் backend Pod-களுக்கும் இடையே ஒரு நெட்வொர்க் port அல்லது சுமை பகிர்வியை (load balancer) வைக்க Kubernetes வழிகளை வழங்குகிறது.

## Service வரையறுத்தல்

ஒரு Service என்பது ஒரு {{< glossary_tooltip text="பொருள்" term_id="object" >}} ஆகும் (Pod அல்லது ConfigMap பொருளைப் போலவே). Kubernetes API-ஐ பயன்படுத்தி Service வரையறைகளை உருவாக்கலாம், பார்க்கலாம் அல்லது மாற்றலாம். வழக்கமாக அந்த API அழைப்புகளை உங்களுக்காக செய்ய `kubectl` போன்ற கருவியைப் பயன்படுத்துவீர்கள்.

எடுத்துக்காட்டாக, ஒவ்வொன்றும் TCP port 9376-இல் கேட்கும் மற்றும் `app.kubernetes.io/name=MyApp` என்று முத்திரையிடப்பட்ட (labelled) Pod-களின் தொகுப்பு உங்களிடம் இருப்பதாக வைத்துக்கொள்வோம். அந்த TCP listener-ஐ வெளியிட ஒரு Service-ஐ வரையறுக்கலாம்:

இந்த manifest-ஐ பயன்படுத்துவது இயல்புநிலை ClusterIP service வகையுடன் "my-service" என்ற புதிய Service-ஐ உருவாக்குகிறது. `app.kubernetes.io/name: MyApp` முத்திரையுடன் எந்த Pod-இலும் TCP port 9376-ஐ Service குறிவைக்கிறது.

Kubernetes இந்த Service-க்கு ஒரு IP முகவரியை (cluster IP) ஒதுக்குகிறது, இது virtual IP address வழிமுறையால் பயன்படுத்தப்படுகிறது.

அந்த Service-க்கான controller தொடர்ச்சியாக அதன் தேர்வாளருடன் பொருந்தும் Pod-களை ஆராய்கிறது, பின்னர் Service-க்கான EndpointSlice-களின் தொகுப்பில் தேவையான புதுப்பிப்புகளை செய்கிறது.

### Port வரையறைகள்

Pod-களில் உள்ள port வரையறைகளுக்கு பெயர்கள் இருக்கின்றன, மேலும் இந்த பெயர்களை Service-இன் `targetPort` பண்புக்கூறில் குறிப்பிடலாம். எடுத்துக்காட்டாக, பின்வரும் வழியில் Service-இன் `targetPort`-ஐ Pod port-உடன் இணைக்கலாம்:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app.kubernetes.io/name: proxy
  ports:
  - name: name-of-service-port
    protocol: TCP
    port: 80
    targetPort: http-web-svc
---
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:
    app.kubernetes.io/name: proxy
spec:
  containers:
  - name: nginx
    image: nginx:stable
    ports:
      - containerPort: 80
        name: http-web-svc
```

ஒரே கட்டமைக்கப்பட்ட பெயரைப் பயன்படுத்தி, வெவ்வேறு port எண்கள் வழியாக அதே நெட்வொர்க் நெறிமுறை கிடைக்கும் Pod-களின் கலவை Service-இல் இருந்தாலும் இது செயல்படும்.

Service-களுக்கான இயல்புநிலை நெறிமுறை TCP ஆகும்; நீங்கள் வேறு ஏதேனும் ஆதரிக்கப்படும் நெறிமுறையையும் பயன்படுத்தலாம்.

பல Service-கள் ஒன்றுக்கும் மேற்பட்ட port-களை வெளிப்படுத்த வேண்டியிருப்பதால், Kubernetes ஒரு Service பொருளில் பல port வரையறைகளை ஆதரிக்கிறது. ஒவ்வொரு port வரையறையும் ஒரே நெறிமுறையையோ அல்லது வேறுபட்ட நெறிமுறையையோ கொண்டிருக்கலாம்.

### தேர்வாளர்கள் இல்லாத Service-கள் {#services-without-selectors}

தேர்வாளரின் (selector) மூலம் Kubernetes Pod-களுக்கான அணுகலை சுருக்கமாக வழங்குவது Service-களின் மிகவும் பொதுவான பயன்பாடு ஆகும், ஆனால் தொடர்புடைய EndpointSlice பொருட்களுடன் மற்றும் தேர்வாளர் இல்லாமல் பயன்படுத்தும்போது, Service மற்ற வகையான backend-களையும் சுருக்கமாக வழங்க முடியும், கொத்துக்கு வெளியே இயங்குபவை உட்பட.

எடுத்துக்காட்டாக:
* உற்பத்தியில் வெளிப்புற தரவுத்தள கொத்தை வைத்திருக்க விரும்புகிறீர்கள், ஆனால் உங்கள் சோதனை சூழலில் உங்கள் சொந்த தரவுத்தளங்களைப் பயன்படுத்துகிறீர்கள்.
* உங்கள் Service-ஐ வேறு Namespace அல்லது வேறு கொத்தில் உள்ள Service-க்கு சுட்டிக்காட்ட விரும்புகிறீர்கள்.
* பணிச்சுமையை Kubernetes-க்கு இடம்பெயர்க்கிறீர்கள். அணுகுமுறையை மதிப்பிடும் போது, உங்கள் backend-களின் ஒரு பகுதியை மட்டும் Kubernetes-இல் இயக்குகிறீர்கள்.

இந்த சூழ்நிலைகளில் எதிலும் Pod-களைப் பொருத்துவதற்கான தேர்வாளரைக் குறிப்பிடாமல் ஒரு Service-ஐ வரையறுக்கலாம். எடுத்துக்காட்டாக:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 9376
```

இந்த Service-க்கு தேர்வாளர் இல்லாததால், தொடர்புடைய EndpointSlice பொருட்கள் தானாக உருவாக்கப்படுவதில்லை. EndpointSlice பொருளை கைமுறையாக சேர்ப்பதன் மூலம் Service-ஐ அது இயங்கும் நெட்வொர்க் முகவரி மற்றும் port-உடன் இணைக்கலாம்.

### EndpointSlice-கள்

EndpointSlice-கள் என்பவை ஒரு Service-க்கான ஆதரவு நெட்வொர்க் முனைப்புள்ளிகளின் துணைக்குழுவை (ஒரு துண்டை) குறிக்கும் பொருட்கள் ஆகும்.

ஒவ்வொரு EndpointSlice எத்தனை முனைப்புள்ளிகளை குறிக்கிறது என்பதை உங்கள் Kubernetes கொத்து கண்காணிக்கிறது. ஒரு Service-க்கு மிக அதிகமான முனைப்புள்ளிகள் இருந்து ஒரு வரம்பை அடைந்தால், Kubernetes மற்றொரு காலி EndpointSlice-ஐ சேர்த்து புதிய முனைப்புள்ளி தகவலை அங்கே சேமிக்கிறது. இயல்புநிலையாக, ஏற்கனவே உள்ள அனைத்து EndpointSlice-களும் குறைந்தது 100 முனைப்புள்ளிகளைக் கொண்டிருக்கும்போது Kubernetes புதிய EndpointSlice-ஐ உருவாக்குகிறது.

### பல-port Service-கள்

சில Service-களுக்கு, ஒன்றுக்கும் மேற்பட்ட port-களை வெளிப்படுத்த வேண்டும். Kubernetes ஒரு Service பொருளில் பல port வரையறைகளை கட்டமைக்க அனுமதிக்கிறது. ஒரு Service-க்கு பல port-களைப் பயன்படுத்தும்போது, அவை தெளிவாக இருக்க அனைத்து port-களுக்கும் பெயர்கள் கொடுக்க வேண்டும்.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app.kubernetes.io/name: MyApp
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 9376
    - name: https
      protocol: TCP
      port: 443
      targetPort: 9377
```

## Service வகை {#publishing-services-service-types}

உங்கள் பயன்பாட்டின் சில பகுதிகளுக்கு (எடுத்துக்காட்டாக, frontend-கள்), கொத்துக்கு வெளியே அணுகக்கூடிய வெளிப்புற IP முகவரியில் ஒரு Service-ஐ வெளிப்படுத்த விரும்பலாம்.

Kubernetes Service வகைகள் நீங்கள் விரும்பும் Service வகையைக் குறிப்பிட அனுமதிக்கின்றன.

கிடைக்கும் type மதிப்புகள் மற்றும் அவற்றின் நடத்தைகள்:

ClusterIP: கொத்து-உள் IP-யில் Service-ஐ வெளிப்படுத்துகிறது. இந்த மதிப்பைத் தேர்ந்தெடுப்பது Service-ஐ கொத்துக்குள் இருந்து மட்டுமே அணுகக்கூடியதாக ஆக்குகிறது. இது இயல்புநிலையாகும்.

NodePort: ஒரு நிலையான port-இல் (NodePort) ஒவ்வொரு Node-இன் IP-யில் Service-ஐ வெளிப்படுத்துகிறது. node port-ஐ கிடைக்கச் செய்ய, Kubernetes ஒரு cluster IP முகவரியை அமைக்கிறது, நீங்கள் type: ClusterIP Service-ஐ கோரியதைப் போலவே.

LoadBalancer: வெளிப்புற சுமை பகிர்வியைப் பயன்படுத்தி Service-ஐ வெளிப்புறமாக வெளிப்படுத்துகிறது. Kubernetes நேரடியாக சுமை சமநிலைப்படுத்தல் கூறுகளை வழங்குவதில்லை; நீங்கள் ஒன்றை வழங்க வேண்டும், அல்லது உங்கள் Kubernetes கொத்தை கிளவுட் வழங்குநருடன் ஒருங்கிணைக்கலாம்.

ExternalName: Service-ஐ externalName புலத்தின் உள்ளடக்கங்களுக்கு இணைக்கிறது (எடுத்துக்காட்டாக, api.foo.bar.example என்ற hostname-க்கு). இந்த இணைப்பு உங்கள் கொத்தின் DNS server-ஐ அந்த வெளிப்புற hostname மதிப்புடன் CNAME record-ஐ திருப்பி அனுப்ப கட்டமைக்கிறது. எந்த வகையான proxy-யும் அமைக்கப்படுவதில்லை.

### type: ClusterIP

இந்த இயல்புநிலை Service வகை, உங்கள் கொத்து அந்த நோக்கத்திற்காக ஒதுக்கிய IP முகவரிகளின் தொகுப்பிலிருந்து ஒரு IP முகவரியை ஒதுக்குகிறது. `.spec.clusterIP`-ஐ `"None"` என அமைத்து Service-ஐ வரையறுத்தால், Kubernetes IP முகவரியை ஒதுக்காது. கூடுதல் தகவலுக்கு headless Service-கள் பகுதியைப் பாருங்கள்.

#### உங்கள் சொந்த IP முகவரியைத் தேர்ந்தெடுத்தல்

Service உருவாக்கும் கோரிக்கையின் ஒரு பகுதியாக உங்கள் சொந்த cluster IP முகவரியைக் குறிப்பிடலாம். இதைச் செய்ய, `.spec.clusterIP` புலத்தை அமைக்கவும்.

### type: NodePort

`type` புலத்தை NodePort என அமைத்தால், Kubernetes கட்டுப்பாட்டு தளம் `--service-node-port-range` flag-ஆல் குறிப்பிடப்பட்ட வரம்பிலிருந்து (இயல்புநிலை: 30000-32767) ஒரு port-ஐ ஒதுக்குகிறது. ஒவ்வொரு node-ம் அந்த port-ஐ உங்கள் Service-க்கு proxy செய்கிறது.

### type: LoadBalancer

வெளிப்புற சுமை பகிர்விகளை ஆதரிக்கும் கிளவுட் வழங்குநர்களில், `type` புலத்தை LoadBalancer என அமைப்பது உங்கள் Service-க்கான சுமை பகிர்வியை வழங்குகிறது.

### type: ExternalName

ExternalName வகை Service-கள் ஒரு Service-ஐ DNS பெயருக்கு இணைக்கின்றன, `my-service` அல்லது `cassandra` போன்ற வழக்கமான தேர்வாளருக்கு அல்ல. இந்த Service-களை `spec.externalName` parameter-உடன் குறிப்பிடுகிறீர்கள்.

## Headless Service-கள்

சில நேரங்களில் சுமை-சமநிலைப்படுத்தல் மற்றும் ஒரு தனி Service IP தேவையில்லை. இந்த வழக்கில், cluster IP முகவரிக்கு (`.spec.clusterIP`) `"None"` என வெளிப்படையாகக் குறிப்பிடுவதன் மூலம் headless Service-கள் என அழைக்கப்படுவதை உருவாக்கலாம்.

Kubernetes-இன் செயலாக்கத்துடன் பிணைக்கப்படாமல் மற்ற சேவை கண்டறிதல் வழிமுறைகளுடன் இடைமுகம் செய்ய headless Service-ஐ பயன்படுத்தலாம்.

## சேவைகளைக் கண்டறிதல்

உங்கள் கொத்துக்குள் இயங்கும் வாடிக்கையாளர்களுக்கு, Kubernetes ஒரு Service-ஐ கண்டறிவதற்கான இரண்டு முதன்மை முறைகளை ஆதரிக்கிறது: சூழல் மாறிகள் மற்றும் DNS.

### சூழல் மாறிகள்

ஒரு Pod ஒரு Node-இல் இயக்கப்படும்போது, kubelet ஒவ்வொரு செயலில் உள்ள Service-க்கும் சூழல் மாறிகளின் தொகுப்பைச் சேர்க்கிறது. இது `{SVCNAME}_SERVICE_HOST` மற்றும் `{SVCNAME}_SERVICE_PORT` மாறிகளைச் சேர்க்கிறது.

### DNS

உங்கள் Kubernetes கொத்துக்கு add-on பயன்படுத்தி DNS சேவையை அமைக்கலாம் (மற்றும் கிட்டத்தட்ட எப்போதும் செய்ய வேண்டும்).

CoreDNS போன்ற கொத்து-அறிவுள்ள DNS server, புதிய Service-களுக்காக Kubernetes API-ஐ கண்காணித்து ஒவ்வொன்றுக்கும் DNS record-களின் தொகுப்பை உருவாக்குகிறது. உங்கள் கொத்து முழுவதும் DNS இயக்கப்பட்டிருந்தால், அனைத்து Pod-களும் தங்கள் DNS பெயரால் Service-களை தானாகவே தீர்க்க முடியும்.

## வெளிப்புற IP-கள்

கொத்து node-களில் ஒன்று அல்லது அதற்கு மேற்பட்டவற்றுக்கு வழிநடத்தும் வெளிப்புற IP-கள் இருந்தால், அந்த externalIP-களில் Kubernetes Service-களை வெளிப்படுத்தலாம்.
