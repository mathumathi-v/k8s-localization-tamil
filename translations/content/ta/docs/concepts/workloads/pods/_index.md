<!-- overview -->

_Pod-கள்_ என்பது Kubernetes-இல் நீங்கள் உருவாக்கி நிர்வகிக்கக்கூடிய மிகச்சிறிய வரிசைப்படுத்தக்கூடிய கணினி அலகுகள் ஆகும்.

ஒரு _Pod_ (திமிங்கலக் கூட்டம் அல்லது பட்டாணி Pod போன்றது) என்பது ஒன்று அல்லது அதற்கு மேற்பட்ட {{< glossary_tooltip text="கொள்கலன்களின்" term_id="container" >}} குழுவாகும், பகிரப்பட்ட சேமிப்பு மற்றும் நெட்வொர்க் வளங்கள், மற்றும் கொள்கலன்களை எவ்வாறு இயக்குவது என்பதற்கான விவரக்குறிப்புடன் கூடியது. ஒரு Pod-இன் உள்ளடக்கங்கள் எப்போதும் இணை-இடத்தில் வைக்கப்பட்டு, இணை-திட்டமிடப்பட்டு, பகிரப்பட்ட சூழலில் இயக்கப்படும். ஒரு Pod ஒரு பயன்பாடு-குறிப்பிட்ட "தர்க்கரீதியான host"-ஐ மாதிரியாக்குகிறது: இது ஒப்பீட்டளவில் இறுக்கமாக இணைக்கப்பட்ட ஒன்று அல்லது அதற்கு மேற்பட்ட பயன்பாட்டு கொள்கலன்களைக் கொண்டுள்ளது. கிளவுட் அல்லாத சூழல்களில், ஒரே இயற்பியல் அல்லது மெய்நிகர் இயந்திரத்தில் செயல்படுத்தப்படும் பயன்பாடுகள் ஒரே தர்க்கரீதியான host-இல் செயல்படுத்தப்படும் கிளவுட் பயன்பாடுகளுக்கு ஒப்பானவை.

பயன்பாட்டு கொள்கலன்களுடன், ஒரு Pod ஆனது Pod தொடக்கத்தின் போது இயங்கும் {{< glossary_tooltip text="init கொள்கலன்களையும்" term_id="init-container" >}} கொண்டிருக்கலாம். இயங்கும் Pod-ஐ debug செய்ய {{< glossary_tooltip text="ephemeral கொள்கலன்களையும்" term_id="ephemeral-container" >}} செலுத்தலாம்.

## Pod என்றால் என்ன?

{{< note >}}
Pod-கள் அங்கு இயங்குவதற்கு, கொத்தில் உள்ள ஒவ்வொரு Node-லும் ஒரு [container runtime](/docs/setup/production-environment/container-runtimes/)-ஐ நிறுவ வேண்டும்.
{{< /note >}}

ஒரு Pod-இன் பகிரப்பட்ட சூழல் என்பது Linux namespace-கள், cgroups மற்றும் சாத்தியமான பிற தனிமைப்படுத்தல் அம்சங்களின் தொகுப்பாகும் - ஒரு {{< glossary_tooltip text="கொள்கலனை" term_id="container" >}} தனிமைப்படுத்தும் அதே விஷயங்கள். ஒரு Pod-இன் சூழலுக்குள், தனிப்பட்ட பயன்பாடுகளுக்கு மேலும் துணை-தனிமைப்படுத்தல்கள் பயன்படுத்தப்படலாம்.

ஒரு Pod என்பது பகிரப்பட்ட namespace-கள் மற்றும் பகிரப்பட்ட கோப்பு முறைமை தொகுதிகளைக் கொண்ட கொள்கலன்களின் தொகுப்பிற்கு ஒத்ததாகும்.

Kubernetes கொத்தில் Pod-கள் இரண்டு முக்கிய வழிகளில் பயன்படுத்தப்படுகின்றன:

* **ஒரு கொள்கலனை இயக்கும் Pod-கள்**. "ஒரு-கொள்கலன்-ஒரு-Pod" மாதிரி மிகவும் பொதுவான Kubernetes பயன்பாட்டு வழக்காகும்; இந்த வழக்கில், ஒரு Pod-ஐ ஒரு கொள்கலனைச் சுற்றிய wrapper என்று நினைக்கலாம்; Kubernetes கொள்கலன்களை நேரடியாக நிர்வகிப்பதை விட Pod-களை நிர்வகிக்கிறது.
* **ஒன்றாக வேலை செய்ய வேண்டிய பல கொள்கலன்களை இயக்கும் Pod-கள்**. ஒரு Pod ஆனது இறுக்கமாக இணைக்கப்பட்ட மற்றும் வளங்களைப் பகிர வேண்டிய [பல இணை-இட கொள்கலன்களால்](#how-pods-manage-multiple-containers) ஆன ஒரு பயன்பாட்டை இணைக்க முடியும். இந்த இணை-இட கொள்கலன்கள் ஒரு ஒற்றை ஒருங்கிணைந்த அலகை உருவாக்குகின்றன.

  ஒரு Pod-இல் பல இணை-இட மற்றும் இணை-நிர்வகிக்கப்படும் கொள்கலன்களை குழுவாக்குவது ஒப்பீட்டளவில் மேம்பட்ட பயன்பாட்டு வழக்காகும். உங்கள் கொள்கலன்கள் இறுக்கமாக இணைக்கப்பட்ட குறிப்பிட்ட நிகழ்வுகளில் மட்டுமே இந்த வடிவத்தைப் பயன்படுத்த வேண்டும்.

  நகலெடுப்பை (resilience அல்லது capacity-க்காக) வழங்க பல கொள்கலன்களை இயக்க வேண்டிய அவசியமில்லை; பல பிரதிகள் தேவைப்பட்டால், [பணிச்சுமை மேலாண்மையைப்](/docs/concepts/workloads/controllers/) பாருங்கள்.

## Pod-களைப் பயன்படுத்துதல்

பின்வருவது `nginx:1.14.2` படத்தை இயக்கும் ஒரு கொள்கலனைக் கொண்ட Pod-இன் உதாரணமாகும்.

{{% code_sample file="pods/simple-pod.yaml" %}}

மேலே காட்டப்பட்ட Pod-ஐ உருவாக்க, பின்வரும் கட்டளையை இயக்கவும்:
```shell
kubectl apply -f https://k8s.io/examples/pods/simple-pod.yaml
```

Pod-கள் பொதுவாக நேரடியாக உருவாக்கப்படுவதில்லை, பணிச்சுமை வளங்களைப் பயன்படுத்தி உருவாக்கப்படுகின்றன. Pod-கள் பணிச்சுமை வளங்களுடன் எவ்வாறு பயன்படுத்தப்படுகின்றன என்பது பற்றிய கூடுதல் தகவலுக்கு [Pod-களுடன் வேலை செய்தல்](#working-with-pods) பகுதியைப் பாருங்கள்.

### Pod-களை நிர்வகிப்பதற்கான பணிச்சுமை வளங்கள்

வழக்கமாக நீங்கள் Pod-களை நேரடியாக உருவாக்க வேண்டியதில்லை, ஒற்றை Pod-கள் கூட. அதற்கு பதிலாக, {{< glossary_tooltip text="Deployment" term_id="deployment" >}} அல்லது {{< glossary_tooltip text="Job" term_id="job" >}} போன்ற பணிச்சுமை வளங்களைப் பயன்படுத்தி அவற்றை உருவாக்குங்கள். உங்கள் Pod-கள் நிலையைக் கண்காணிக்க வேண்டும் என்றால், {{< glossary_tooltip text="StatefulSet" term_id="statefulset" >}} வளத்தைக் கருத்தில் கொள்ளுங்கள்.

ஒவ்வொரு Pod-ம் கொடுக்கப்பட்ட பயன்பாட்டின் ஒரு நிகழ்வை இயக்க வடிவமைக்கப்பட்டுள்ளது. உங்கள் பயன்பாட்டை கிடைமட்டமாக அளவிட விரும்பினால் (மேலும் நிகழ்வுகளை இயக்குவதன் மூலம் மொத்த வளங்களை வழங்க), ஒவ்வொரு நிகழ்வுக்கும் ஒன்றாக பல Pod-களைப் பயன்படுத்த வேண்டும். Kubernetes-இல், இது பொதுவாக _நகலெடுப்பு_ என்று குறிப்பிடப்படுகிறது. நகலெடுக்கப்பட்ட Pod-கள் வழக்கமாக ஒரு பணிச்சுமை வளம் மற்றும் அதன் {{< glossary_tooltip text="கட்டுப்படுத்தியால்" term_id="controller" >}} ஒரு குழுவாக உருவாக்கப்பட்டு நிர்வகிக்கப்படுகின்றன.

Kubernetes பணிச்சுமை வளங்களையும், அவற்றின் கட்டுப்படுத்திகளையும் பயன்பாட்டு அளவிடல் மற்றும் தன்-குணப்படுத்தலை எவ்வாறு செயல்படுத்த பயன்படுத்துகிறது என்பது பற்றிய கூடுதல் தகவலுக்கு [Pod-கள் மற்றும் கட்டுப்படுத்திகள்](#pods-and-controllers) பகுதியைப் பாருங்கள்.

Pod-கள் தங்கள் உள்ளடங்கிய கொள்கலன்களுக்கு இரண்டு வகையான பகிரப்பட்ட வளங்களை இயல்பாக வழங்குகின்றன: [நெட்வொர்க்கிங்](#pod-networking) மற்றும் [சேமிப்பு](#pod-storage).

## Pod-களுடன் வேலை செய்தல்

Kubernetes-இல் நீங்கள் தனிப்பட்ட Pod-களை நேரடியாக அரிதாகவே உருவாக்குவீர்கள் — ஒற்றை Pod-கள் கூட. ஏனென்றால் Pod-கள் ஒப்பீட்டளவில் தற்காலிகமான, நீக்கக்கூடிய நிறுவனங்களாக வடிவமைக்கப்பட்டுள்ளன. ஒரு Pod உருவாக்கப்படும்போது (நேரடியாக உங்களால் அல்லது மறைமுகமாக ஒரு {{< glossary_tooltip text="கட்டுப்படுத்தியால்" term_id="controller" >}}), புதிய Pod உங்கள் கொத்தில் உள்ள ஒரு {{< glossary_tooltip term_id="node" >}}-இல் இயங்கத் திட்டமிடப்படுகிறது. Pod அந்த Node-இல் செயலாக்கம் முடியும் வரை, Pod பொருள் நீக்கப்படும் வரை, வள பற்றாக்குறையால் Pod *வெளியேற்றப்படும்* வரை, அல்லது Node செயலிழக்கும் வரை இருக்கும்.

{{< note >}}
ஒரு Pod-இல் கொள்கலனை மறுதொடக்கம் செய்வது Pod-ஐ மறுதொடக்கம் செய்வதுடன் குழப்பப்படக்கூடாது. ஒரு Pod என்பது ஒரு செயல்முறை அல்ல, கொள்கலன்(களை) இயக்குவதற்கான சூழல். ஒரு Pod நீக்கப்படும் வரை நிலைத்திருக்கும்.
{{< /note >}}

ஒரு Pod-இன் பெயர் சரியான [DNS subdomain](/docs/concepts/overview/working-with-objects/names#dns-subdomain-names) மதிப்பாக இருக்க வேண்டும், ஆனால் இது Pod hostname-க்கு எதிர்பாராத முடிவுகளை உருவாக்கலாம். சிறந்த இணக்கத்தன்மைக்கு, பெயர் [DNS label](/docs/concepts/overview/working-with-objects/names#dns-label-names)-க்கான மிகவும் கட்டுப்படுத்தப்பட்ட விதிகளைப் பின்பற்ற வேண்டும்.

### Pod இயங்குதளம்

{{< feature-state state="stable" for_k8s_version="v1.25" >}}

Pod எந்த இயங்குதளத்தில் இயங்க வேண்டும் என்பதைக் குறிக்க `.spec.os.name` புலத்தை `windows` அல்லது `linux` என அமைக்க வேண்டும். இவை இரண்டு மட்டுமே தற்போது Kubernetes ஆதரிக்கும் இயங்குதளங்கள். எதிர்காலத்தில், இந்த பட்டியல் விரிவுபடுத்தப்படலாம்.

Kubernetes v{{< skew currentVersion >}}-இல், `.spec.os.name`-இன் மதிப்பு {{< glossary_tooltip text="kube-scheduler" term_id="kube-scheduler" >}} Pod-ஐ இயக்க ஒரு Node-ஐ தேர்ந்தெடுக்கும் விதத்தை பாதிக்காது. Node-களை இயக்குவதற்கு ஒன்றுக்கு மேற்பட்ட இயங்குதளங்கள் உள்ள எந்த கொத்திலும், ஒவ்வொரு Node-லும் [kubernetes.io/os](/docs/reference/labels-annotations-taints/#kubernetes-io-os) முத்திரையை சரியாக அமைக்க வேண்டும், மற்றும் இயங்குதள முத்திரையின் அடிப்படையில் `nodeSelector`-உடன் Pod-களை வரையறுக்க வேண்டும். kube-scheduler உங்கள் Pod-ஐ பிற அளவுகோல்களின் அடிப்படையில் ஒரு Node-க்கு ஒதுக்குகிறது, மேலும் அந்த Pod-இல் உள்ள கொள்கலன்களுக்கு Node இயங்குதளம் சரியாக இருக்கும் இடத்தில் பொருத்தமான Node-ஐ தேர்ந்தெடுப்பதில் வெற்றி பெறலாம் அல்லது பெறாமல் போகலாம். [Pod security standards](/docs/concepts/security/pod-security-standards/) இயங்குதளத்திற்கு பொருந்தாத கொள்கைகளை செயல்படுத்துவதைத் தவிர்க்க இந்த புலத்தையும் பயன்படுத்துகின்றன.

### Pod-கள் மற்றும் கட்டுப்படுத்திகள்

உங்களுக்காக பல Pod-களை உருவாக்கி நிர்வகிக்க பணிச்சுமை வளங்களைப் பயன்படுத்தலாம். வளத்திற்கான கட்டுப்படுத்தி நகலெடுப்பு மற்றும் rollout-ஐ கையாளுகிறது மற்றும் Pod தோல்வி ஏற்பட்டால் தானியங்கி குணப்படுத்தலைச் செய்கிறது. எடுத்துக்காட்டாக, ஒரு Node செயலிழந்தால், ஒரு கட்டுப்படுத்தி அந்த Node-இல் உள்ள Pod-கள் வேலை செய்வதை நிறுத்தியதைக் கவனித்து மாற்று Pod-ஐ உருவாக்குகிறது. திட்டமிடுபவர் மாற்று Pod-ஐ ஆரோக்கியமான Node-இல் வைக்கிறது.

ஒன்று அல்லது அதற்கு மேற்பட்ட Pod-களை நிர்வகிக்கும் பணிச்சுமை வளங்களின் சில உதாரணங்கள் இங்கே:

* {{< glossary_tooltip text="Deployment" term_id="deployment" >}}
* {{< glossary_tooltip text="StatefulSet" term_id="statefulset" >}}
* {{< glossary_tooltip text="DaemonSet" term_id="daemonset" >}}

### Pod வார்ப்புருக்கள்

{{< glossary_tooltip text="பணிச்சுமை" term_id="workload" >}} வளங்களுக்கான கட்டுப்படுத்திகள் _pod வார்ப்புருவிலிருந்து_ Pod-களை உருவாக்கி, உங்கள் சார்பாக அந்த Pod-களை நிர்வகிக்கின்றன.

PodTemplate-கள் என்பது Pod-களை உருவாக்குவதற்கான விவரக்குறிப்புகள் ஆகும், இவை [Deployment-கள்](/docs/concepts/workloads/controllers/deployment/), [Job-கள்](/docs/concepts/workloads/controllers/job/) மற்றும் [DaemonSet-கள்](/docs/concepts/workloads/controllers/daemonset/) போன்ற பணிச்சுமை வளங்களில் சேர்க்கப்பட்டுள்ளன.

ஒவ்வொரு பணிச்சுமை வளத்திற்கான கட்டுப்படுத்தியும் உண்மையான Pod-களை உருவாக்க பணிச்சுமை பொருளுக்குள் உள்ள `PodTemplate`-ஐ பயன்படுத்துகிறது. `PodTemplate` என்பது உங்கள் பயன்பாட்டை இயக்க நீங்கள் பயன்படுத்திய எந்த பணிச்சுமை வளத்தின் விரும்பிய நிலையின் ஒரு பகுதியாகும்.

ஒரு Pod-ஐ உருவாக்கும்போது, Pod-இல் இயங்கும் கொள்கலன்களுக்கான Pod வார்ப்புருவில் [சூழல் மாறிகளை](/docs/tasks/inject-data-application/define-environment-variable-container/) சேர்க்கலாம்.

கீழே உள்ள மாதிரி ஒரு எளிய Job-க்கான manifest ஆகும், இது ஒரு கொள்கலனைத் தொடங்கும் `template`-ஐக் கொண்டுள்ளது. அந்த Pod-இல் உள்ள கொள்கலன் ஒரு செய்தியை அச்சிட்டு பிறகு இடைநிறுத்தப்படும்.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: hello
spec:
  template:
    # இது pod template ஆகும்
    spec:
      containers:
      - name: hello
        image: busybox:1.28
        command: ['sh', '-c', 'echo "Hello, Kubernetes!" && sleep 3600']
      restartPolicy: OnFailure
    # pod template இங்கே முடிகிறது
```

Pod template-ஐ மாற்றுவது அல்லது புதிய pod template-க்கு மாறுவது ஏற்கனவே இருக்கும் Pod-கள் மீது நேரடி விளைவை ஏற்படுத்தாது. ஒரு பணிச்சுமை வளத்திற்கான pod template-ஐ மாற்றினால், அந்த வளம் புதுப்பிக்கப்பட்ட template-ஐ பயன்படுத்தும் மாற்று Pod-களை உருவாக்க வேண்டும்.

எடுத்துக்காட்டாக, StatefulSet கட்டுப்படுத்தி ஒவ்வொரு StatefulSet பொருளுக்கும் இயங்கும் Pod-கள் தற்போதைய pod template-உடன் பொருந்துவதை உறுதிசெய்கிறது. StatefulSet-ஐ அதன் pod template-ஐ மாற்ற திருத்தினால், StatefulSet புதுப்பிக்கப்பட்ட template-இன் அடிப்படையில் புதிய Pod-களை உருவாக்கத் தொடங்குகிறது. இறுதியில், பழைய Pod-கள் அனைத்தும் புதிய Pod-களால் மாற்றப்படுகின்றன, மேலும் புதுப்பிப்பு நிறைவடைகிறது.

ஒவ்வொரு பணிச்சுமை வளமும் Pod template-இல் ஏற்படும் மாற்றங்களைக் கையாள அதன் சொந்த விதிகளை செயல்படுத்துகிறது. StatefulSet பற்றி குறிப்பாக மேலும் படிக்க விரும்பினால், StatefulSet Basics பயிற்சிக்கட்டுரையில் [Update strategy](/docs/tutorials/stateful-application/basic-stateful-set/#updating-statefulsets) பகுதியைப் படிக்கவும்.

Node-களில், {{< glossary_tooltip term_id="kubelet" text="kubelet" >}} pod template-கள் மற்றும் புதுப்பிப்புகள் பற்றிய எந்த விவரங்களையும் நேரடியாக கவனிக்கவோ நிர்வகிக்கவோ செய்யாது; அந்த விவரங்கள் சுருக்கமாக மறைக்கப்பட்டுள்ளன. அந்த சுருக்கமும் கவலைகளின் பிரிப்பும் அமைப்பின் சொற்பொருளை எளிமையாக்குகிறது, மேலும் ஏற்கனவே உள்ள குறியீட்டை மாற்றாமல் கொத்தின் நடத்தையை விரிவுபடுத்துவதை சாத்தியமாக்குகிறது.

## Pod புதுப்பிப்பு மற்றும் மாற்றீடு

முந்தைய பகுதியில் குறிப்பிட்டபடி, ஒரு பணிச்சுமை வளத்திற்கான Pod template மாற்றப்படும்போது, கட்டுப்படுத்தி ஏற்கனவே உள்ள Pod-களை புதுப்பிக்கவோ திருத்தவோ செய்யாமல் புதுப்பிக்கப்பட்ட template-இன் அடிப்படையில் புதிய Pod-களை உருவாக்குகிறது.

Pod-களை நேரடியாக நிர்வகிப்பதை Kubernetes தடுக்காது. இயங்கும் Pod-இன் சில புலங்களை இடத்திலேயே புதுப்பிக்க முடியும். எனினும், [`patch`](/docs/reference/generated/kubernetes-api/{{< param "version" >}}/#patch-pod-v1-core) மற்றும் [`replace`](/docs/reference/generated/kubernetes-api/{{< param "version" >}}/#replace-pod-v1-core) போன்ற Pod புதுப்பிப்பு செயல்பாடுகளுக்கு சில வரம்புகள் உள்ளன:

- ஒரு Pod பற்றிய metadata-வின் பெரும்பகுதி மாற்ற இயலாதது. எடுத்துக்காட்டாக, `namespace`, `name`, `uid` அல்லது `creationTimestamp` புலங்களை மாற்ற இயலாது.
- `metadata.deletionTimestamp` அமைக்கப்பட்டிருந்தால், `metadata.finalizers` பட்டியலில் புதிய உள்ளீடு எதுவும் சேர்க்க இயலாது.
- Pod புதுப்பிப்புகள் `spec.containers[*].image`, `spec.initContainers[*].image`, `spec.activeDeadlineSeconds`, `spec.terminationGracePeriodSeconds`, `spec.tolerations` அல்லது `spec.schedulingGates` தவிர பிற புலங்களை மாற்றக்கூடாது. `spec.tolerations`-க்கு, புதிய உள்ளீடுகளை மட்டுமே சேர்க்க முடியும்.
- `spec.activeDeadlineSeconds` புலத்தை புதுப்பிக்கும்போது, இரண்டு வகையான புதுப்பிப்புகள் அனுமதிக்கப்படுகின்றன:
  1. ஒதுக்கப்படாத புலத்தை ஒரு நேர்மறை எண்ணாக அமைத்தல்;
  1. புலத்தை ஒரு நேர்மறை எண்ணிலிருந்து சிறிய, எதிர்மறையற்ற எண்ணாக புதுப்பித்தல்.

## வளப் பகிர்வு மற்றும் தொடர்பு

Pod-கள் அவற்றின் உள்ளடங்கிய கொள்கலன்களிடையே தரவு பகிர்வு மற்றும் தொடர்பை செயல்படுத்துகின்றன.

### Pod-களில் சேமிப்பு {#pod-storage}

ஒரு Pod பகிரப்பட்ட சேமிப்பு {{< glossary_tooltip text="தொகுதிகளின்" term_id="volume" >}} தொகுப்பை குறிப்பிடலாம். Pod-இல் உள்ள அனைத்து கொள்கலன்களும் பகிரப்பட்ட தொகுதிகளை அணுகலாம், இது அந்த கொள்கலன்கள் தரவைப் பகிர அனுமதிக்கிறது. தொகுதிகள் ஒரு Pod-இல் உள்ள நிலையான தரவை, உள்ளே உள்ள கொள்கலன்களில் ஒன்றை மறுதொடக்கம் செய்ய வேண்டிய நிலையிலும் நிலைத்திருக்க அனுமதிக்கின்றன. Kubernetes பகிரப்பட்ட சேமிப்பை எவ்வாறு செயல்படுத்துகிறது மற்றும் Pod-களுக்கு கிடைக்கச் செய்கிறது என்பது பற்றிய கூடுதல் தகவலுக்கு [சேமிப்பு](/docs/concepts/storage/) பகுதியைப் பாருங்கள்.

### Pod நெட்வொர்க்கிங்

ஒவ்வொரு Pod-க்கும் ஒவ்வொரு முகவரி குடும்பத்திற்கும் ஒரு தனித்துவமான IP முகவரி ஒதுக்கப்படுகிறது. ஒரு Pod-இல் உள்ள ஒவ்வொரு கொள்கலனும் IP முகவரி மற்றும் நெட்வொர்க் port-கள் உட்பட நெட்வொர்க் namespace-ஐ பகிர்ந்துகொள்கிறது. ஒரு Pod-க்குள் (**மட்டுமே** அப்போது), Pod-க்கு சொந்தமான கொள்கலன்கள் `localhost`-ஐ பயன்படுத்தி ஒன்றுக்கொன்று தொடர்பு கொள்ளலாம். ஒரு Pod-இல் உள்ள கொள்கலன்கள் Pod-க்கு *வெளியே* உள்ள நிறுவனங்களுடன் தொடர்பு கொள்ளும்போது, பகிரப்பட்ட நெட்வொர்க் வளங்களை (port-கள் போன்றவை) எவ்வாறு பயன்படுத்துவது என்பதை ஒருங்கிணைக்க வேண்டும். ஒரு Pod-க்குள், கொள்கலன்கள் ஒரு IP முகவரி மற்றும் port இடத்தைப் பகிர்ந்துகொள்கின்றன, மேலும் `localhost` வழியாக ஒன்றையொன்று கண்டறியலாம். ஒரு Pod-இல் உள்ள கொள்கலன்கள் SystemV semaphore-கள் அல்லது POSIX பகிரப்பட்ட நினைவகம் போன்ற நிலையான இடை-செயல்முறை தொடர்புகளைப் பயன்படுத்தியும் ஒன்றுக்கொன்று தொடர்பு கொள்ளலாம். வெவ்வேறு Pod-களில் உள்ள கொள்கலன்கள் வேறுபட்ட IP முகவரிகளைக் கொண்டுள்ளன, மேலும் சிறப்பு உள்ளமைவு இல்லாமல் OS-நிலை IPC மூலம் தொடர்பு கொள்ள இயலாது. வேறு Pod-இல் இயங்கும் கொள்கலனுடன் தொடர்பு கொள்ள விரும்பும் கொள்கலன்கள் IP நெட்வொர்க்கிங்-ஐ பயன்படுத்தி தொடர்பு கொள்ளலாம்.

Pod-க்குள் உள்ள கொள்கலன்கள் அமைப்பின் hostname-ஐ Pod-க்கு உள்ளமைக்கப்பட்ட `name`-ஆகவே பார்க்கின்றன. இதைப் பற்றி [நெட்வொர்க்கிங்](/docs/concepts/cluster-administration/networking/) பகுதியில் மேலும் தகவல் உள்ளது.

## Pod பாதுகாப்பு அமைப்புகள் {#pod-security}

Pod-கள் மற்றும் கொள்கலன்கள் மீது பாதுகாப்பு கட்டுப்பாடுகளை அமைக்க, Pod விவரக்குறிப்பில் `securityContext` புலத்தைப் பயன்படுத்துங்கள். இந்த புலம் ஒரு Pod அல்லது தனிப்பட்ட கொள்கலன்கள் என்ன செய்ய முடியும் என்பதில் விரிவான கட்டுப்பாட்டை உங்களுக்கு வழங்குகிறது. மேலும் விவரங்களுக்கு [Advanced Pod Configuration](/docs/concepts/workloads/pods/advanced-pod-config/) பகுதியைப் பாருங்கள்.

அடிப்படை பாதுகாப்பு உள்ளமைவுக்கு, Baseline Pod security standard-ஐ பூர்த்தி செய்து கொள்கலன்களை non-root ஆக இயக்க வேண்டும். எளிய security context-களை அமைக்கலாம்:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-context-demo
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
  - name: sec-ctx-demo
    image: busybox
    command: ["sh", "-c", "sleep 1h"]
```

capabilities, seccomp profile-கள் மற்றும் விரிவான பாதுகாப்பு விருப்பங்கள் உட்பட மேம்பட்ட security context உள்ளமைவுக்கு, [பாதுகாப்பு கருத்துக்கள்](/docs/concepts/security/) பகுதியைப் பாருங்கள்.

* Pod-கள் மற்றும் கொள்கலன்களுக்கு நீங்கள் பயன்படுத்தக்கூடிய kernel-நிலை பாதுகாப்பு கட்டுப்பாடுகளைப் பற்றி அறிய, [Linux kernel security constraints for Pods and containers](/docs/concepts/security/linux-kernel-security-constraints) பகுதியைப் பாருங்கள்.
* Pod security context பற்றி மேலும் அறிய, [Configure a Security Context for a Pod or Container](/docs/tasks/configure-pod-container/security-context/) பகுதியைப் பாருங்கள்.

## வள கோரிக்கைகள் மற்றும் வரம்புகள்

ஒரு Pod-ஐ குறிப்பிடும்போது, ஒவ்வொரு கொள்கலனுக்கும் எவ்வளவு வளம் தேவை என்பதை விருப்பமாக குறிப்பிடலாம். குறிப்பிடப்படும் மிகவும் பொதுவான வளங்கள் CPU மற்றும் நினைவகம் (RAM) ஆகும்.

ஒரு Pod-இல் உள்ள கொள்கலன்களுக்கான வள _கோரிக்கையை_ குறிப்பிடும்போது, Pod-ஐ எந்த Node-இல் வைக்க வேண்டும் என்பதை முடிவு செய்ய kube-scheduler இந்த தகவலைப் பயன்படுத்துகிறது. ஒரு கொள்கலனுக்கு வள _வரம்பை_ குறிப்பிடும்போது, இயங்கும் கொள்கலன் நீங்கள் அமைத்த வரம்பை விட அதிகமான வளத்தைப் பயன்படுத்த அனுமதிக்கப்படாத வகையில் kubelet அந்த வரம்புகளை செயல்படுத்துகிறது.

CPU வரம்புகள் CPU throttling மூலம் செயல்படுத்தப்படுகின்றன. ஒரு கொள்கலன் அதன் CPU வரம்பை நெருங்கும்போது, kernel அதன் CPU அணுகலைக் கட்டுப்படுத்துகிறது. நினைவக வரம்புகள் ஒரு கொள்கலன் அதன் வரம்பை மீறும்போது out-of-memory (OOM) kill-கள் மூலம் kernel-ஆல் செயல்படுத்தப்படுகின்றன.

{{< note >}}
CPU வரம்புகளை அமைப்பது ஒரு சமநிலையை உள்ளடக்கியது. CPU வரம்புகள் ஒரே Node-இல் உள்ள மற்ற பணிச்சுமைகளை ஒரு பணிச்சுமை பட்டினிக்கு ஆளாக்கும் noisy neighbor சிக்கல்களைத் தடுக்க உதவுகின்றன. பல-குத்தகைதாரர் சூழல்களில் இது குறிப்பாக முக்கியமானது. எனினும், Node-இல் உபரி CPU திறன் இருக்கும்போதும் CPU வரம்புகள் throttling-ஐ ஏற்படுத்தலாம், இது latency-உணர்திறன் கொண்ட பணிச்சுமை செயல்திறனைக் குறைக்கலாம். CPU வரம்புகளை அமைக்க வேண்டுமா என்பது உங்கள் சூழல், பணிச்சுமை பண்புகள் மற்றும் தனிமைப்படுத்தல் தேவைகளைப் பொறுத்தது.
{{< /note >}}

வள அலகுகள், செயல்படுத்தல் நடத்தை மற்றும் உள்ளமைவு உதாரணங்களுக்கு, [Resource Management for Pods and Containers](/docs/concepts/configuration/manage-resources-containers/) பகுதியைப் பாருங்கள்.

## நிலையான Pod-கள்

_நிலையான Pod-கள்_ (Static Pods) {{< glossary_tooltip text="API server" term_id="kube-apiserver" >}} அவற்றை கவனிக்காமல், ஒரு குறிப்பிட்ட Node-இல் kubelet daemon-ஆல் நேரடியாக நிர்வகிக்கப்படுகின்றன. பெரும்பாலான Pod-கள் கட்டுப்பாட்டு தளத்தால் நிர்வகிக்கப்படுகின்றன (எடுத்துக்காட்டாக, ஒரு {{< glossary_tooltip text="Deployment" term_id="deployment" >}}), நிலையான Pod-களுக்கு, kubelet ஒவ்வொரு நிலையான Pod-ஐயும் நேரடியாக மேற்பார்வையிடுகிறது (மற்றும் அது தோல்வியடைந்தால் மறுதொடக்கம் செய்கிறது).

நிலையான Pod-கள் எப்போதும் ஒரு குறிப்பிட்ட Node-இல் உள்ள ஒரு {{< glossary_tooltip term_id="kubelet" >}}-உடன் பிணைக்கப்பட்டிருக்கும். நிலையான Pod-களின் முக்கிய பயன்பாடு தன்-ஹோஸ்ட் செய்யப்பட்ட கட்டுப்பாட்டு தளத்தை இயக்குவது: வேறுவிதமாகச் சொன்னால், தனிப்பட்ட [கட்டுப்பாட்டு தள கூறுகளை](/docs/concepts/architecture/#control-plane-components) மேற்பார்வையிட kubelet-ஐ பயன்படுத்துவது.

kubelet தானாகவே ஒவ்வொரு நிலையான Pod-க்கும் Kubernetes API server-இல் ஒரு {{< glossary_tooltip text="mirror Pod" term_id="mirror-pod" >}}-ஐ உருவாக்க முயற்சிக்கிறது. இதன் பொருள் ஒரு Node-இல் இயங்கும் Pod-கள் API server-இல் தெரியும், ஆனால் அங்கிருந்து கட்டுப்படுத்த இயலாது. மேலும் தகவலுக்கு [Create static Pods](/docs/tasks/configure-pod-container/static-pod) வழிகாட்டியைப் பாருங்கள்.

{{< note >}}
ஒரு நிலையான Pod-இன் `spec` பிற API பொருள்களைக் குறிப்பிட இயலாது (எ.கா., {{< glossary_tooltip text="ServiceAccount" term_id="service-account" >}}, {{< glossary_tooltip text="ConfigMap" term_id="configmap" >}}, {{< glossary_tooltip text="Secret" term_id="secret" >}} போன்றவை).
{{< /note >}}

## பல கொள்கலன்களைக் கொண்ட Pod-கள் {#how-pods-manage-multiple-containers}

Pod-கள் ஒரு ஒருங்கிணைந்த சேவை அலகை உருவாக்கும் பல ஒத்துழைக்கும் செயல்முறைகளை (கொள்கலன்களாக) ஆதரிக்க வடிவமைக்கப்பட்டுள்ளன. ஒரு Pod-இல் உள்ள கொள்கலன்கள் தானாகவே கொத்தில் உள்ள ஒரே இயற்பியல் அல்லது மெய்நிகர் இயந்திரத்தில் இணை-இடத்தில் வைக்கப்பட்டு இணை-திட்டமிடப்படுகின்றன. கொள்கலன்கள் வளங்களையும் சார்புகளையும் பகிர்ந்துகொள்ளலாம், ஒன்றுக்கொன்று தொடர்பு கொள்ளலாம், மற்றும் எப்போது, எவ்வாறு நிறுத்தப்படுகின்றன என்பதை ஒருங்கிணைக்கலாம்.

Kubernetes கொத்தில் Pod-கள் இரண்டு முக்கிய வழிகளில் பயன்படுத்தப்படுகின்றன:

* **ஒரு கொள்கலனை இயக்கும் Pod-கள்**. "ஒரு-கொள்கலன்-ஒரு-Pod" மாதிரி மிகவும் பொதுவான Kubernetes பயன்பாட்டு வழக்காகும்; இந்த வழக்கில், ஒரு Pod-ஐ ஒரு கொள்கலனைச் சுற்றிய wrapper என்று நினைக்கலாம்; Kubernetes கொள்கலன்களை நேரடியாக நிர்வகிப்பதை விட Pod-களை நிர்வகிக்கிறது.
* **ஒன்றாக வேலை செய்ய வேண்டிய பல கொள்கலன்களை இயக்கும் Pod-கள்**. ஒரு Pod ஆனது இறுக்கமாக இணைக்கப்பட்ட மற்றும் வளங்களைப் பகிர வேண்டிய பல இணை-இட கொள்கலன்களால் ஆன ஒரு பயன்பாட்டை இணைக்க முடியும். இந்த இணை-இட கொள்கலன்கள் ஒரு ஒற்றை ஒருங்கிணைந்த சேவை அலகை உருவாக்குகின்றன — எடுத்துக்காட்டாக, ஒரு கொள்கலன் பகிரப்பட்ட தொகுதியில் சேமிக்கப்பட்ட தரவை பொதுமக்களுக்கு வழங்குகிறது, அதே நேரத்தில் ஒரு தனி {{< glossary_tooltip text="sidecar கொள்கலன்" term_id="sidecar-container" >}} அந்த கோப்புகளை புதுப்பிக்கிறது அல்லது மாற்றுகிறது. Pod இந்த கொள்கலன்களை, சேமிப்பு வளங்களை மற்றும் ஒரு தற்காலிக நெட்வொர்க் அடையாளத்தை ஒரு அலகாக இணைக்கிறது.

எடுத்துக்காட்டாக, பகிரப்பட்ட தொகுதியில் உள்ள கோப்புகளுக்கான வலை சேவையகமாக செயல்படும் ஒரு கொள்கலனும், தொலைநிலை மூலத்திலிருந்து அந்த கோப்புகளைப் புதுப்பிக்கும் ஒரு தனி [sidecar கொள்கலனும்](/docs/concepts/workloads/pods/sidecar-containers/) இருக்கலாம், பின்வரும் வரைபடத்தில் காட்டப்பட்டுள்ளது:

{{< figure src="/images/docs/pod.svg" alt="Pod creation diagram" class="diagram-medium" >}}

சில Pod-கள் {{< glossary_tooltip text="app கொள்கலன்களுடன்" term_id="app-container" >}} {{< glossary_tooltip text="init கொள்கலன்களையும்" term_id="init-container" >}} கொண்டுள்ளன. முன்னிருப்பாக, init கொள்கலன்கள் app கொள்கலன்கள் தொடங்கப்படுவதற்கு முன் இயங்கி நிறைவடைகின்றன.

முக்கிய பயன்பாட்டு Pod-க்கு துணை சேவைகளை வழங்கும் [sidecar கொள்கலன்களையும்](/docs/concepts/workloads/pods/sidecar-containers/) கொண்டிருக்கலாம் (எடுத்துக்காட்டாக: ஒரு service mesh).

{{< feature-state feature_gate_name="SidecarContainers" >}}

முன்னிருப்பாக செயல்படுத்தப்பட்ட `SidecarContainers` [feature gate](/docs/reference/command-line-tools-reference/feature-gates/) init கொள்கலன்களுக்கு `restartPolicy: Always` என்று குறிப்பிட அனுமதிக்கிறது. `Always` restart policy-ஐ அமைப்பது, நீங்கள் அமைத்த கொள்கலன்கள் Pod-இன் முழு வாழ்நாள் முழுவதும் இயங்கும் _sidecar-களாக_ கருதப்படுவதை உறுதிசெய்கிறது. நீங்கள் வெளிப்படையாக sidecar கொள்கலன்களாக வரையறுக்கும் கொள்கலன்கள் முக்கிய பயன்பாட்டு Pod-க்கு முன் தொடங்கி Pod நிறுத்தப்படும் வரை இயங்கிக் கொண்டிருக்கும்.

## கொள்கலன் probe-கள்

ஒரு _probe_ என்பது kubelet ஒரு கொள்கலனில் அவ்வப்போது செய்யும் ஒரு கண்டறிதல் ஆகும். கண்டறிதல் செய்ய, kubelet வெவ்வேறு செயல்களைத் தொடங்கலாம்:

- `ExecAction` (container runtime உதவியுடன் செய்யப்படுகிறது)
- `TCPSocketAction` (kubelet-ஆல் நேரடியாக சரிபார்க்கப்படுகிறது)
- `HTTPGetAction` (kubelet-ஆல் நேரடியாக சரிபார்க்கப்படுகிறது)

Pod Lifecycle ஆவணத்தில் [probe-கள்](/docs/concepts/workloads/pods/pod-lifecycle/#container-probes) பற்றி மேலும் படிக்கலாம்.
